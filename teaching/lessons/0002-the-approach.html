The approach: a small local AI as supervisor, not as the thermostat itself

The headline idea in one sentence: a local language model looks at the building every 4 simulated hours and decides two numbers; a much simpler, non-AI program applies and double-checks that decision every 15 minutes in between.

First: what is an LLM, in the terms this project needs

An LLM (large language model) is software that takes text in and produces text out, shaped by whatever instructions and data you give it. This project uses qwen2.5:3b-instruct — "3b" means about 3 billion parameters, which is small by LLM standards (deliberately — it runs entirely on one local machine via Ollama, a program that serves LLMs locally, no cloud, no API cost, no internet required). You don't need to know how the model works internally for this project; you need to know what it's asked to do and how its output is checked, because a small model's mistakes are exactly what the rest of the system exists to catch.

What the model is actually asked to produce

Not code, not a plan, not prose — one small JSON object:

{"heating_c": 20.0, "cooling_c": 24.5, "reason": "occupied, mild day, widen deadband"}

Two numbers and a one-line justification. That narrowness is intentional: the smaller and more structured the ask, the more reliable a 3B model can be made (more in Lesson 5).

The core design choice: supervisory, not per-timestep

The obvious-sounding approach — call the AI at every single 15-minute control step — was tried in reasoning and rejected by arithmetic, not intuition:

Per-timestep controlSupervisory (chosen)
Simulated period3 weeks3 weeks
Control timesteps2,0162,016
Times the AI is actually asked2,016126
Time spent waiting on the AI~110 minutes~5.8 minutes
The physics simulation itself12 seconds12 seconds

Calling a model every timestep would make the AI roughly 550× the cost of the physics it's supposedly steering. So the model was demoted from "controller" to supervisor: it sets policy (a heating/cooling pair) that holds for 4 simulated hours, and a plain, deterministic Python loop applies that policy at every 15-minute timestep in between, with its own safety checks running independently.

Why this isn't just a shortcut This mirrors how real Building Management Systems (BMS) actually work: slow supervisory logic resets setpoints occasionally; fast local control loops track them continuously. It's also more stable — a policy that holds for four hours can't oscillate at 15-minute frequency the way a model re-deciding every timestep might.

The two loops, side by side

Inner loop — every 15 minutes, always running reads the current policy → clamps it into a safe range → checks occupancy → writes it to the actuators. No AI involved. Never skipped.
↑ supplies a policy to hold, every 4h ↑
Outer loop — every 4 simulated hours reads sensors + energy usage → asks the LLM → validates the reply → hands the inner loop a new policy, or fails safe if it can't.

Why "AI decides, code verifies" instead of "trust the AI"

Because the model is small (3B parameters) and therefore will occasionally be wrong or malformed, nothing the model outputs reaches the actual building equipment unchecked. Every proposal passes through a validation stack before it can touch anything:

→
2. Schema checkis it even valid JSON with the right fields?

3. Safety clamphard numeric limits, whatever the source
→
4. Occupancy checkcontext-aware: different rules occupied vs. empty

Full detail on each layer is Lesson 4 (architecture) and Lesson 5 (why each one exists). The point to take away here: this project's stance is "the AI proposes, deterministic code disposes" — never the reverse.

What "closed loop" means, precisely

This is not the model analyzing a spreadsheet of past data offline. The model is consulted while a live physics simulation is running, reads its current sensor state, and its decision is written back into that same running simulation to affect what happens next. Data genuinely moves in both directions, continuously, for the whole 3-week run. That's what makes it a closed loop rather than an analysis report.

Quick check: if per-timestep control is unaffordable, why not just make the AI faster instead of calling it less often?
Because even a faster model wouldn't remove the deeper problem: control at 15-minute resolution needs to be predictable and stable, and an LLM re-deciding that often can drift or oscillate. Slower supervisory cadence plus a deterministic inner loop is the more correct design, not just the affordable one — see the "Why this isn't just a shortcut" callout above.
