The workflow: from one command to a savings report

Two levels here. First the macro pipeline — what happens when you run the project end to end. Then the micro cycle — what happens inside one supervisory decision, which repeats 126 times per run.

Macro: one command, five stages

python src/prepare_model.py
python src/run_experiment.py --mode all
python src/export_idf.py
python dashboard/build_report.py
1. prepare_model.py Takes the untouched EnergyPlus example file, trims the run period to 3 weeks, strips ~40 unneeded outputs, adds back only the timestep-resolution readings the control loop needs. Writes models/simulation.idf.
↓
2. run_experiment.py --mode all Runs the same instrumented model three times, back to back, changing only the controller: baseline (does nothing) → rule-based (hand-written logic) → agent (the LLM supervisor). Each run writes results/<mode>/metrics.json + timeseries.csv.
↓
3. export_idf.py Reads everything the agent actually applied at each of 2,016 timesteps, takes the median setpoint per (weekday/weekend, hour) bucket, and bakes that into a real, standalone EnergyPlus file: models/agent_optimized.idf — runs with no AI, no MCP, no Python at all.
↓
4. build_report.py Reads every mode's results and writes one self-contained HTML dashboard with 5 charts — no server, no network needed to view it.

Total wall clock: about 6 minutes, almost all of it spent waiting on the LLM during the agent run (the physics itself takes 12 seconds — see Lesson 2's table).

Micro: what happens inside one supervisory decision

This is the cycle that repeats every 4 simulated hours (126 times across the 3-week run). It crosses three separate processes — worth sitting with, because it's the part most worth being able to draw on a whiteboard in an interview.

SENSE EnergyPlus finishes a zone timestep → runner callback reads temperatures, humidity, outdoor weather, occupancy, energy so far → writes it to runtime_state.json (atomic file write).
↓ every 4h, the agent is due →
TOOL CALL Agent calls get_building_state and get_energy_summary over MCP → the MCP server (a separate process) reads that same JSON file and replies.
↓
PROMPT Agent builds a prompt: current readings, the legal setpoint range right now, and the last 6 decisions as a compact table → sends it to Ollama with a JSON schema constraint.
↓
LLM REPLY qwen2.5:3b-instruct returns {heating_c, cooling_c, reason} as JSON.
↓
VALIDATE Agent calls the set_setpoints MCP tool. It clamps the numbers into the safety envelope and — if occupancy makes the request unsafe — rejects it with a specific reason instead of silently fixing it.
↓ rejected? → reason is appended to the conversation, model retries (max 2) → still failing? → rule-based controller takes this interval
ACT Accepted policy is written to pending_policy.json. The next 15-minute timestep's inner loop picks it up, re-clamps it against current occupancy (the operating envelope), and writes it to the actual heating/cooling schedule actuators.
Worth noticing The validation and the acting happen in different timesteps, by design. The MCP tool validates against the safety envelope once, when the policy is proposed. The inner loop then re-guards it independently on every timestep it's in force — because occupancy can change between now and 4 hours from now, and a setback chosen at 04:00 must not still be in force at 06:00 when people arrive.

Why three processes, not one script

ProcessRole
EnergyPlus simulation
(in the main Python process)		Runs the physics; its callbacks sense and actuate.
MCP server
(separate subprocess, stdio)		Exposes 5 tools to the agent; cannot see the simulation's Python objects directly, so it reads/writes small JSON files instead.
Ollama
(local LLM server)		Actually runs the model and returns a JSON reply.

This separation is not incidental complexity — it's what makes the "MCP tool layer" a genuine communication bus rather than the agent just calling Python functions directly. More on why that matters for the project's evaluation criteria in Lesson 6.

Quick check: why does SENSE (writing runtime_state.json) happen even on timesteps where no decision is due?
Because the dashboard, the "vs. baseline so far" comparison, and any tool call the agent makes need up-to-date sensor data at all times — not just at the moment of a decision. Publishing every timestep keeps the state file fresh regardless of the 4-hour decision cadence.
