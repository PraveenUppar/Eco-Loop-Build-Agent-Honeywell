System design and architecture

Four things an interviewer will want you to draw from memory: the process boundary, how data crosses it safely, the callback model inside EnergyPlus, and the defense-in-depth safety stack. This lesson is the one to re-read right before the interview.

The full component diagram

EnergyPlus process (in-process Python API) Runs the physics. Two callbacks hook into it: one to actuate, one to sense+decide (see below). Holds the safety clamp and operating envelope.
↕ atomic JSON files: runtime_state.json (sim→tools), pending_policy.json (tools→sim)
MCP server process (separate, stdio) Exposes 5 tools: get_building_state, get_energy_summary, set_setpoints, read_simulation_errors, list_zones. Cannot see the sim's Python objects, so it only ever talks through those two files.
↕ MCP protocol calls, via a background-thread event loop (mcp_bridge.py)
Agent supervisor (agent.py) Builds the prompt, calls the model, applies self-correction, tracks the decision cache.
↕ chat request/response
Ollama (local LLM server) Runs qwen2.5:3b-instruct, returns schema-constrained JSON.

Why the callback model, and why two callbacks not one

EnergyPlus's Python API lets you register functions that fire at specific points in its simulation loop. This project uses exactly two:

CallbackJobWhy this one
begin_system_timestep_
before_predictor		Actuate Fires before the zone predictor computes heating/cooling loads, so a setpoint written here actually affects this timestep. Any later and it'd be a timestep too late.
end_zone_timestep_
after_zone_reporting		Sense + decide Fires exactly once per zone timestep. EnergyPlus can internally shorten the system timestep during difficult HVAC iterations — reading energy meters in the actuation callback would double-count. This callback is the one guaranteed once-per-zone-timestep hook.

A controller (baseline / rule-based / agent) never touches an actuator directly — it only returns a Policy object; the runner clamps and applies it. That indirection is what makes the safety layer non-optional: there's no code path that skips it.

Crossing the process boundary safely

The MCP server is a separate process from the simulation — it can't import the simulation's Python objects, so the two talk through two small JSON files, written with os.replace (atomic on NTFS — a reader can never observe a half-written file).

A real bug, worth knowing about On Windows, os.replace raises WinError 5 if the destination file happens to be open in another process at that instant. With the MCP server polling state while the simulation writes it 2,016 times, this fired constantly in early testing. Fix: a short bounded retry on both sides, treating the state file as telemetry — a dropped write is fine, because the next timestep republishes a fresh one 15 minutes later. Killing the simulation over a missed write would have been the wrong trade.

Calling an async tool from a synchronous callback

The EnergyPlus callback is an ordinary synchronous Python function. The MCP client session, however, is asyncio-based and needs to stay open for the entire run. mcp_bridge.py resolves this by running the whole async session on its own event loop in a background thread, and the callback submits work to it with run_coroutine_threadsafe. This is what lets the agent talk to a real MCP server over stdio, rather than the easier shortcut of just importing the tool functions and calling them directly in-process.

The safety stack (defense in depth)

Nothing reaches a real actuator without passing through all of this, regardless of where the policy came from:

clamp_pair()Hard numeric bounds: heating 18–22 °C, cooling 23–27 °C, deadband ≥ 1.5 °C. Non-numeric, NaN, inf, booleans, and inverted pairs all resolve to a safe fallback — nothing crashes, nothing passes through unclamped.
↓
set_setpoints tool checkContext-aware: OCCUPIED rejects cooling above 25 °C; EMPTY rejects cooling below 26 °C (that would run the AC for nobody). Rejections carry the specific reason — this is what drives self-correction.
↓
operating_envelope()Runs every 15-minute timestep, independent of what the supervisor asked 4 hours ago. Pulls setpoints into the comfort band if occupied; pushes them to setback if empty.

The third layer is the one that's easy to underrate: the supervisor only re-plans every 4 hours, so without an independent per-timestep guard, a setback policy chosen at 04:00 (nobody home) would still be legally "in force" — and silently applied — at 06:00 when people start arriving.

Config as the single source of truth

src/config.py is the one file every other module imports from for zone names, schedule names, safety limits, and the run period. That's a deliberate architectural choice: the runner, the MCP server, the agent's prompt, and the dashboard all need to agree on, say, what "occupied" means — having one file own that avoids the classic bug of four places disagreeing about a limit after only three get updated.

Quick check: if the operating envelope already re-guards every timestep, why does the MCP tool layer also need to reject unsafe requests?
Because the tool-layer rejection is what feeds self-correction — it hands the model a specific, actionable reason it can react to on retry. The operating envelope alone would silently override an unsafe policy without ever telling the model it was wrong, so the model would keep proposing the same mistake every cycle instead of learning within the conversation.
Ask me to trace one specific piece of data — say, an outdoor temperature reading — all the way from the EnergyPlus callback to the LLM's prompt. Following one value through every hop cements this diagram faster than re-reading it.
