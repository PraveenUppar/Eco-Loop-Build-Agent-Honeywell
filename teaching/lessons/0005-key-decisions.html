Eco-Loop · Lesson 5 of 10

Decisions made, and why

Every one of these is a real fork in the road where a simpler, worse option was available and rejected on purpose. Interviewers probe exactly this list — "why didn't you just—" — so each entry below states the alternative that was passed over.

The prompt taught the mechanism, not a rulebook — because rules didn't generalize

This is the single best story in the project, worth telling in full.

What went wrong first The first system prompt just listed instructions: "raise cooling_c to save energy." On hot days the model chose cooling_c 23.5 °C — the most expensive legal option — reasoning that since it was hot outside, more cooling was needed. That's backwards: cooling_c is a threshold, and lowering it makes the AC start earlier, not "cool harder for free."

The failure was diagnosable precisely because it was a conceptual error, not an instruction-following error — the model wasn't ignoring the rule, it was pattern-matching "hot → cool harder" without understanding what the number it was setting actually controlled. The fix was rewriting the prompt to explain the mechanism: what a setpoint is, what the deadband is, why raising cooling_c saves energy, and naming the specific misconception directly. A model that understands the mechanism generalizes to situations no rulebook enumerated; a model following memorized rules doesn't.

Structured output (JSON schema) instead of parsing prose

DecisionOllama is given an explicit JSON schema via the format parameter, not just format: "json" or free text.
WhyReliability on a small model can't come from "asking politely." A schema constraint does more for it than any prompt wording — the measured result across every reported run is 0 malformed JSON responses.
Alternative rejectedParsing free-text replies with regex — fragile against a 3B model's inconsistent phrasing.

History as a fixed 6-row table, not a growing transcript

DecisionThe model sees only its last 6 decisions, as a compact table (time, setpoints, cumulative kWh, mean zone temp) — not a running conversation log.
WhyPrompt cost stays bounded regardless of run length (~1,000 tokens per decision, budget target 1,500), while the trend information the model actually needs stays visible.
Alternative rejectedPassing the full conversation transcript — cost would grow unboundedly over a long run.

The legal range restated on every single call

DecisionEvery prompt repeats the currently-binding constraint: e.g. "ALLOWED NOW (people present): heating_c 20.0–22.0, cooling_c 23.0–25.0."
WhyThe occupied comfort limit is the constraint a small model violates most often. Stating it fresh in the user turn — where a small model weights instructions most — cut tool rejections sharply.
Alternative rejectedStating limits once in the system prompt and trusting the model to remember them across a multi-hour conversation.

Self-correction via real tool rejection, not silent clamping

DecisionWhen set_setpoints rejects a policy, the specific reason is appended to the conversation and the model gets up to 2 retries.
WhyA specific, actionable error ("cooling_c 27.0 exceeds the comfort limit 25.0") gives the model something to fix. Result: 17 rejections in the reported run, 16 recovered by self-correction.
Alternative rejectedSilently clamping bad values without telling the model — cheaper, but the model would keep proposing the same mistake every cycle, and you'd lose the diagnostic signal entirely.

A bucketed decision cache

DecisionCache key = (hour // 4, occupied, round(outdoor_temp), round(mean_zone_temp)) — a rounded, bucketed situation, not exact state.
Why02:00 on two consecutive empty weeknights at the same outdoor temperature is the same decision. Rounding is what makes the cache hit at all — exact float state never repeats. Result: 31.7% hit rate over 3 weeks, rising to 59.8% over a full season (more repeats to find as the horizon grows).
Alternative rejectedExact-match caching on raw sensor values — would essentially never hit.

Guaranteed fallback, never "no policy"

DecisionIf the model still can't produce a usable policy after retries, the rule-based controller's target takes that interval — the building is never left without an active policy.
WhyA control system that can silently do nothing is worse than one that falls back to a known-decent default. Measured: 1 fallback in 126 decisions (3-week run), 5 in 552 (season-long endurance run) — under 1% either way.

Exporting the median policy per (day-type, hour) bucket

Decisionexport_idf.py doesn't replay the agent's exact per-timestep decisions — it takes the median applied setpoint for each (weekday/weekend, hour) bucket and bakes that into a standalone schedule.
WhyThe median discards a 3B model's occasional outlier decision. This is exactly why the exported IDF beats the live agent (3.79% vs 3.32% savings, both at 0% comfort violations) — that gap is the model's run-to-run inconsistency, quantified and then filtered out.

A real MCP subprocess, not a direct function call

DecisionThe agent talks to the tools over an actual MCP client/server connection across two processes (stdio transport), via a background-thread event loop — not by importing and calling the tool functions in-process.
WhyThis is what makes "the agent uses tools" a genuine architectural claim rather than a convenient abstraction — the agent really cannot see or touch the simulation except through the same interface any other MCP client would use.

Quick check: what's the common thread across all of these?
Every one trades a small amount of extra engineering for either reliability on a small model, honest measurement, or graceful degradation. None of them are about making the model "smarter" — they're about making the system work well despite using a small, sometimes wrong, local model. That framing — "the validation layer does real work because the model is 3B" — is the project's central engineering thesis.
