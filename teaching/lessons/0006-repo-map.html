Repo map: what every folder and file is for

A guided tour, organized by role rather than alphabetically — grouped the way you'd explain it out loud.

Top-level folders

FolderContents
src/All the Python: runner, safety layer, MCP server/bridge, agent, metrics, experiment driver, tests.
models/The EnergyPlus building files (.idf) — see below.
results/Metrics and timeseries written by each experiment run, one subfolder per controller mode, plus results/endurance/ for the season-long run.
results_2week/, results_3week/ Earlier snapshots of results from different run-length experiments, kept for comparison/audit rather than actively used.
dashboard/build_report.py (generates the charts) and the generated report.html output.

src/ — every file, one line each

FilePurpose
config.pySingle source of truth: zone names, schedule names, safety limits, run period. Everything else imports from here.
prepare_model.pyTrims the stock example IDF to the run week and instruments it with timestep-resolution outputs.
eplus_runner.pyThe in-process EnergyPlus runner — the two callbacks (sense, actuate), handle resolution, the main run loop.
policy.pyPolicy dataclass, clamp_pair/clamp_policy, and operating_envelope — the safety layer.
controllers.pyDeterministic controllers: FixedController (diagnostic-only) and RuleBasedController (comparison arm + fallback).
mcp_server.pyThe FastMCP stdio server exposing the 5 tools.
mcp_bridge.pySynchronous facade over the async MCP client session, running it on a background thread.
agent.pyThe LLM supervisor: system prompt, JSON schema, self-correction loop, decision cache, telemetry.
shared_state.pyAtomic cross-process JSON read/write (runtime_state.json, pending_policy.json), including the Windows sharing-violation retry.
log_tools.pyFilter → dedupe → truncate pipeline for EnergyPlus .err logs.
metrics.pyComputes kWh, peak kW, comfort violation % from eplusout.csv — the authoritative source, not the live meter readings.
run_experiment.pyRuns one or all three controller modes and writes results/summary.json.
export_idf.pyBakes the agent's applied setpoints into standalone agent_optimized.idf.
compare_models.pySide experiment: identical loop, a different local model, to isolate model-choice effects.
endurance_run.pyRuns the full pipeline over a whole cooling season (June–August) to check nothing degrades over a longer horizon.
make_stress_log.pyGenerates a synthetic warning-heavy .err file to exercise log_tools.py's compression on a harder case than this project's own (clean) logs produce.
package_submission.pyBundles the deliverables into the submission/ archive.
test_clamp.pyUnit tests: throws hostile input at the safety clamp (strings, NaN, booleans, inverted pairs, malformed payloads).
test_actuation.pyProves the actuators are genuinely connected — a loose deadband must lower energy, a tight one must raise it.
test_mcp_client.pyStandalone MCP client that starts a real simulation in a background thread and exercises all 5 tools while it's running.

models/ — the three IDFs, and what "IDF" even is

An IDF (Input Data File) is EnergyPlus's native building description format — geometry, zones, schedules, systems, all as plain text objects.

FileWhat it is
baseline.idfThe untouched 5ZoneAirCooled example, exactly as EnergyPlus ships it.
simulation.idfBuilt by prepare_model.py: same building, trimmed run period, instrumented outputs.
agent_optimized.idfBuilt by export_idf.py after a real agent run — the agent's learned policy, reconstructed into real Schedule:Compact objects. Runs standalone.

Why agent_optimized.idf has to be reconstructed at all: actuating the EnergyPlus API during a run changes values only in memory — nothing about "what the agent actually did" persists to a file on its own. This script is what turns a live decision-making process into a portable, inspectable artifact.

The documentation files, and what each is actually for

FileAudience / purpose
README.mdFront door: setup instructions, the one-command run, the results table, and the honest-limitations section. Written for someone deciding whether to run the project.
ARCHITECTURE.mdThe technical deep-dive, structured around 4 required sections: tool-calling architecture, prompt engineering strategy, latency management, and log-handling. Written for someone evaluating how it's built — this is effectively the source material for Lessons 3–5 here.
SUBMISSION.mdA deliverable-to-evaluation-criteria map: for each grading criterion (System Integration 30%, Energy Efficiency 25%, Comfort 20%, Agentic Autonomy 15%, Documentation 10%), it states exactly where the evidence lives and cites the reproducing command. Written for a grader/evaluator, not a general reader.
docs/presentation.mdSlide-by-slide content for a 6-slide pitch deck (this is a Smart India Hackathon / SIH-style submission), mapped onto a provided template.
docs/DEMO_SCRIPT.mdA timed shot list and narration script for a <3-minute demo video, including the exact commands to run live on camera.
Interview framing If asked "what's the difference between ARCHITECTURE.md and SUBMISSION.md," the crisp answer is: ARCHITECTURE.md explains how the system works; SUBMISSION.md explains where to find proof it works, organized around someone else's grading rubric rather than around the system itself.
Quick check: which file would you open to find why the "Electricity:Facility" meter isn't used directly?
src/config.py — the comment on FACILITY_METERS explains that the aggregate meter doesn't resolve to a usable handle in this EnergyPlus version, so three sector meters (Building/HVAC/Plant electricity) are summed instead, verified to match the facility total exactly.
