What each column actually measures

ColumnMeaning
kWhTotal facility electricity over the 3-week run — lights, plug loads, and HVAC combined.
HVAC kWhJust the setpoint-controllable end uses: cooling, fans, heating, pumps. This is the number the controller can actually influence.
Peak kWThe single highest instantaneous demand across the run — matters for utility demand charges, separate from total energy.
Comfort violations% of occupied zone-timestep readings that fell outside 20–25 °C. The unconditioned plenum is excluded.
Why HVAC% is the fairer number Lights and plug loads are roughly 70% of facility electricity, and no thermostat policy can touch them. Reporting 3.32% facility savings without also stating 11.5% HVAC savings would understate what the controller is actually doing — and reporting only the HVAC number would overstate the building's total electricity impact. Both are reported, on purpose.
Why the exported IDF beats the live agent 3.79% vs. 3.32%, both at 0% comfort violations. The export takes the median applied setpoint per (day-type, hour) bucket (Lesson 5), which discards a 3B model's occasional outlier decision. That gap between "what the model did on average" and "what it did on its worst moments" is the model's run-to-run inconsistency, made visible as a number instead of an assumption.

Agent telemetry — and the arithmetic behind it

1 / 126fell back to rule-based
3.27smedian latency
0safety-clamp violations

llm_calls counts every model invocation, retries included — it is not the decision count. The actual relationship, straight from agent.py's summary():

decisions = llm_calls - retries + cache_hits
          = 102       - 16      + 40         = 126

Read that as: each of the 126 decisions cost either a cache hit (free) or one model call plus however many retries it needed to pass validation.

The endurance run — the same pipeline over a full season

The 3-week figure is the reported headline, but it doesn't by itself prove the loop holds up over a long horizon. endurance_run.py runs the identical pipeline over 1 June – 31 August.

Two claims this run supports that the 3-week run alone can't: the three "must never happen" counters (clamp violations, comfort breaches, malformed JSON) stay at exactly zero across 4.4× the timesteps — the failure rate doesn't grow with horizon length. And the cache improves with scale, because a longer horizon revisits more repeated (hour, occupancy, outdoor, indoor) states — the marginal cost of each additional simulated day falls as the run gets longer, the opposite of the usual scaling worry with an LLM in the loop. Savings are slightly lower over the season for an honest reason: June and August are milder than the July peak week, so there's less cooling load to save on in the first place.

What the dashboard actually shows

dashboard/build_report.py produces one self-contained report.html — no server, no network — with five charts: cumulative electricity by mode, daily electricity, zone temperature vs. the comfort band, setpoint trajectory with LLM decision markers, and a latency histogram for the model calls. Rebuilding it is one command; every number on it traces back to a results/*/metrics.json or timeseries.csv file, never a hand-typed figure.

Quick check: if someone asks "did the AI actually help, or would any controller have done this?" — what's the number that answers it?
The 1.05 percentage-point gap between the rule-based controller (+2.27%) and the LLM agent (+3.32%). The rule-based run isolates "the value of having any controller instead of a static schedule"; the gap above it is what the LLM's situational reasoning specifically contributed.
