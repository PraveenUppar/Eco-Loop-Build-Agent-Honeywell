EnergyPlus — the physics engine underneath everything

EnergyPlus is a whole-building energy simulation engine (originally developed for the U.S. Department of Energy) that models heat transfer, airflow, HVAC systems, and equipment loads at a physical level — not a toy approximation. This project uses it two ways:

  • As a subprocess normally, run via its command-line interface with an IDF + weather file.
  • In-process, via pyenergyplus — this project's actual mode. The Python API lets code register callback functions that fire at specific points during the simulation loop (Lesson 4), which is what makes the "closed loop while the simulation is running" claim literally true rather than a simulated approximation.

Ollama — the local LLM server

Ollama is a program that downloads and serves language models locally — no cloud account, no per-call API cost, no network dependency at inference time. This project pulls one model:

ollama pull qwen2.5:3b-instruct

qwen2.5:3b-instruct is an instruction-tuned model (trained to follow prompts/instructions rather than just continue text) at the 3-billion-parameter size — small enough to run on a single laptop with acceptable latency (median 3.27s per call), which is precisely why the rest of the system exists to compensate for a small model's unreliability rather than assuming a large, expensive cloud model.

MCP — Model Context Protocol, from first principles

MCP is a standard way for an AI application to expose a defined set of tools (callable functions with typed arguments and descriptions) to a model, over a well-specified protocol — instead of every project inventing its own ad hoc function-calling glue.

MCP clientthe agent's side — lists available tools, calls them, gets results back
↔ stdio transport (this project) ↔
MCP servermcp_server.py, launched as a separate process, exposing 5 tools

stdio transport means the client and server talk over the server subprocess's standard input/output streams — no network port, no sockets, just a pipe. This project's server is launched with StdioServerParameters(command=sys.executable, args=[...]) and communicates with a plain ClientSession from the MCP SDK. FastMCP (used in mcp_server.py) is a thin decorator-based framework — @mcp.tool() above a function turns it into a tool the protocol exposes automatically, including generating the schema from the function's type hints and docstring.

Structured output / JSON schema constraints

Separate from MCP: when the agent asks Ollama for a decision, it passes a JSON schema in the format parameter (Lesson 5). This is a different mechanism from tool calling — it constrains the shape of the model's raw text output, rather than letting the model choose to invoke a function. Worth being able to distinguish the two if asked: tool calling is how the agent reads sensors and writes setpoints (through MCP); structured output is how the model's own reply gets forced into valid JSON in the first place.

Quick check: why does the agent talk to EnergyPlus data through MCP tools instead of just reading Python objects directly, given they're conceptually "the same process"?
They're actually not the same process — the MCP server is a genuinely separate subprocess (Lesson 4), so it literally cannot import the simulation's Python objects even if it wanted to. But even setting that aside, going through MCP tools is what makes "the agent uses tools with validated inputs/outputs" a real architectural property instead of the agent having unrestricted access to internal state.
