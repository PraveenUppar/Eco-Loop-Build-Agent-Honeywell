Baseline vs. rule-based vs. LLM agent — side by side

The whole point of running three controllers against the identical building, weather, and run period is that the only variable left is the controller itself — which makes this comparison the cleanest evidence in the whole project. This lesson closes the curriculum by tying every earlier lesson's numbers to the actual controller logic that produced them.

1. Baseline — does nothing

class BaselineController:
    name = "baseline"
    actuates = False

    def decide(self, state):
        return None

The IDF's own factory-default schedules run untouched — the 1.7 °C occupied deadband from Lesson 1. This is the reference point everything else is measured against, not a strawman: it's what a real building runs today if nobody revisits its schedule.

2. Rule-based — hand-written logic, no AI

class RuleBasedController:
    OCCUPIED = (20.0, 24.5)
    UNOCCUPIED = (18.0, 27.0)

    def target_for(self, state):
        return self.OCCUPIED if state.occupied else self.UNOCCUPIED

One if statement. Widen the deadband to 20.0–24.5 °C when occupied (still inside the 20–25 °C comfort band, but much wider than baseline's 1.7 °C) and to a nearly maximal 18.0–27.0 °C when empty. No sensing beyond "is anyone here," no reasoning about outdoor temperature, no adaptation. This controller plays two roles in the project: a comparison arm, and the safe target the LLM agent falls back to when it can't produce a usable policy (Lesson 5).

3. LLM agent — situational reasoning within the same legal bounds

Covered in full in Lessons 2–5. The key structural difference from rule-based: the agent's allowed range when occupied is actually wider than what rule-based ever uses — heating 20.0–22.0, cooling 23.0–25.0 depending on conditions — and it chooses where in that range to sit based on outdoor temperature, recent energy use, and trend, instead of one fixed pair.

The number that isolates the AI's contribution +2.27% → +3.32% is a 1.05 percentage-point gap, entirely attributable to the LLM's situational reasoning — because rule-based already captures "the value of having any controller instead of a static schedule." Peak demand tells the same story: rule-based cuts peak 2.79%, the agent cuts it 3.73%.

Why the comparison is fair (identical everything except the controller)

  • Same IDF (simulation.idf), same weather file, same 3-week run period, same safety clamp and comfort definition.
  • Comfort violations are 0.00% for all three — savings were not bought with comfort. If any controller had traded comfort for savings, that number alone would flag it.
  • Metrics are all computed the same way, from the same authoritative source (eplusout.csv), by the same metrics.py function (Lesson 7) — no controller gets a different measurement method.

A fourth, unlisted controller worth knowing about

FixedController holds one constant setpoint pair for an entire run and deliberately opts out of the comfort guard (enforce_comfort = False). It's not part of the 3-way comparison — its job is purely diagnostic, used by test_actuation.py to prove the actuators are genuinely wired up: a loose deadband must measurably lower energy, and a tight one must measurably raise it, relative to baseline. If both directions don't move energy, something is silently disconnected. Good to mention if asked how the project verifies its own instrumentation, separate from verifying its results.

Quick check: could the rule-based controller's 20.0–24.5 °C band have simply been copied into the LLM's allowed range to get the same result without any AI?
No — the rule-based band is one fixed pair, applied identically on a mild day and a hot day. The agent's advantage isn't a wider fixed band, it's choosing where inside the legal range to sit based on outdoor temperature and recent energy trend, call by call. Copying the fixed pair would reproduce rule-based's result, not the agent's.
