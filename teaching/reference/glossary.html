Glossary

Every term used across the 10 lessons, in one place, grouped by category. Designed to print or scan quickly before the interview — not to read start to finish.

Building control fundamentals

setpointA threshold temperature, not a target — equipment switches on when the room crosses it. This project has two: heating_c and cooling_c. See Lesson 1.
deadbandThe gap between heating_c and cooling_c. Nothing runs while the room is inside it — a wider deadband means less electricity spent.
HVACHeating, Ventilation, and Air Conditioning — the building systems this project's setpoints control.
VAVVariable Air Volume — an HVAC system type that varies how much conditioned air it delivers, rather than always delivering a fixed amount. The building in this project is VAV with reheat.
zoneOne controllable region of a building with its own temperature sensor and setpoint. This project has 5 conditioned zones plus 1 excluded plenum.
plenumAn unconditioned space (here, a return-air plenum) with no thermostat control and no occupants — excluded from both control and the comfort metric.
occupancy scheduleData describing when a zone is expected to have people in it — drives which comfort/safety rules apply at any given moment.
comfort band20–25 °C in this project — the range occupied zones must stay within. Violations are measured only during occupied hours.
setbackDeliberately widening setpoints during unoccupied hours (here, heating ≤19 °C / cooling ≥26 °C) since nobody can be uncomfortable, so any equipment running is pure waste.
PMVPredicted Mean Vote — the standard (ASHRAE 55) thermal-comfort model accounting for humidity, air speed, clothing, and metabolic rate, not just air temperature. This project uses a simpler temperature-band metric instead (Lesson 9).
BMSBuilding Management System — the real-world class of software this project's supervisory/inner-loop split is modeled on.
demand (kW) vs. energy (kWh)kWh is total electricity consumed over a period; kW (demand) is the instantaneous rate — peak kW matters separately because utilities often charge for it directly.

EnergyPlus specifics

EnergyPlusThe whole-building physics simulation engine this project runs, in-process, via its Python API.
IDFInput Data File — EnergyPlus's native plain-text building description format (geometry, zones, schedules, systems).
EPW / TMY3EnergyPlus Weather file format; TMY3 ("Typical Meteorological Year") is a real-location weather dataset used to drive the simulation — Chicago, here.
Schedule:CompactThe IDF object type used for the heating/cooling setpoint schedules — actuating it overrides its value for that timestep.
callbackA Python function registered with the EnergyPlus API that fires automatically at a specific point in the simulation loop. This project uses two — see Lesson 4.
handleAn integer reference EnergyPlus hands back for a named variable/meter/actuator, resolved once and reused every timestep for fast lookups.
actuatorA handle that can be written to, not just read — this project actuates the heating and cooling schedule values.
meterAn EnergyPlus energy-accounting handle (e.g. Cooling:Electricity) summed over time to get kWh.
timestepThe simulation's control resolution — 15 minutes here (4 per hour), 2,016 total across the 3-week run.
warmup / sizing / design daySimulation phases EnergyPlus runs before and around the actual reporting period, explicitly filtered out by a run-period guard so they never contaminate results.

AI / LLM / agent concepts

LLMLarge Language Model — software that generates text (here, JSON) from a prompt. This project uses qwen2.5:3b-instruct, run locally via Ollama.
parameters (3B)A rough size measure for a model — "3B" ≈ 3 billion learned numeric weights. Smaller models are cheaper/faster to run locally but less reliable, which is why this project's validation layer exists.
instruction-tunedA model specifically trained to follow prompts/instructions (vs. just continuing arbitrary text) — the "-instruct" in the model name.
system prompt / user promptThe system prompt sets standing context and rules for the whole conversation (here: what a setpoint is, the hard limits); the user prompt carries the per-call situational data (current readings, allowed range, recent history).
temperature (sampling)A model-output-randomness setting; this project uses 0.2 (low) for more deterministic, repeatable decisions.
structured output / JSON schemaConstraining a model's raw output to match a specific JSON shape, passed via Ollama's format parameter — different from tool calling (see below). See Lesson 5 and 8.
tool calling / function callingLetting a model (or the code orchestrating it) invoke defined external functions with typed arguments — here, the 5 MCP tools.
agent / agentic loopSoftware that reads state, decides, acts, and observes the result, repeatedly. "Agent supervisor" in this project cycles: sense → tool calls → prompt → validate → act.
supervisory controlThe AI sets slow-changing policy (every 4h); a separate deterministic loop applies and enforces it continuously (every 15 min). See Lesson 2.
self-correctionFeeding a rejected attempt's specific failure reason back to the model and letting it retry, rather than giving up or silently overriding it.
fallbackThe safe default (here, the rule-based controller's target) used when the model produces nothing usable after retries — the building is never left without a policy.
decision cacheReusing a past decision for a "bucketed" (rounded, near-identical) situation instead of calling the model again.
latencyTime from asking the model to getting a reply — 3.27s median here, the reason for supervisory rather than per-timestep cadence.
tokenA chunk of text an LLM processes cost/length in — this project budgets ~1,000 tokens per decision.

MCP and systems concepts

MCPModel Context Protocol — a standard for exposing tools to an AI client over a defined protocol. See Lesson 8.
MCP server / clientThe server exposes tools (here: 5, in mcp_server.py); the client (the agent) calls them and reads results.
stdio transportClient and server communicate over the server subprocess's standard input/output streams — no network port involved.
FastMCPA decorator-based framework (@mcp.tool()) for building an MCP server with minimal boilerplate.
asyncio / event loopPython's built-in framework for concurrent I/O-bound code; the MCP client session runs on its own event loop in a background thread here, because it must stay open for the whole run while the EnergyPlus callback stays synchronous.
run_coroutine_threadsafeThe specific asyncio function used to submit work from the synchronous callback thread to the background event loop thread.
atomic writeA file write that a reader can never observe half-finished — done here via write-to-temp-file then os.replace, which is atomic on NTFS.
race conditionA bug caused by two processes/threads touching shared state at an unpredictable relative time — the motivation for atomic writes and the bounded-retry fix around Windows' WinError 5.
defense in depthStacking multiple independent safety checks so no single failure point can let something unsafe through — the clamp → tool check → operating envelope stack (Lesson 4).

Project-specific shorthand

PolicyThe dataclass carrying a heating/cooling setpoint pair plus its source and reason — the one object every controller returns.
clampForcing a value into a safe numeric range, regardless of where it came from.
operating envelopeThe per-timestep, occupancy-aware re-guard that runs independently of the 4-hourly supervisor decision.
baseline / rule-based / agentThe three controller modes compared head-to-head — see Lesson 10.
median-per-bucket exportHow agent_optimized.idf is built: median applied setpoint per (day-type, hour), discarding outlier decisions.
endurance runThe season-long (June–August) rerun used to check nothing degrades over a longer horizon than the reported 3-week experiment.
